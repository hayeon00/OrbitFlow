## A. 현재 구현 분석

### A-1. 기술 스택

| 구성 | 실제 구현 |
|---|---|
| 프레임워크 | Spring Boot 4.0, Java 17, LangChain4j 0.35.0 |
| 임베딩 | OpenAI `text-embedding-3-small` (`global/config/ChatbotConfig.java`) |
| LLM | OpenAI `gpt-4o-mini`, temperature 0 |
| 벡터 DB | ChromaDB 0.4.21 (k8s `k8s/infra/chromadb.yaml`), 단일 컬렉션 `orbitflow_manuals` |
| 메타데이터 DB | MySQL `manual_metadata`, `manual_category`, `chat_conversation`, `chat_message` |
| 원본 파일 | S3 (`FileService`, `FileDomain.CHAT`) |
| 테넌시 | **다중 회사(멀티테넌트)**. JWT의 `companyId`, 모든 엔티티의 `company_id`, 모든 청크 메타데이터의 `company_id`로 구분 |

### A-2. 데이터 흐름 (실제 코드 기준)

```
[관리자 UI] admin-chatbot-manual.html / chatbot-manual.js
   │ POST /api/admin/manual/upload  (ROLE ADMIN·COMPANY_ADMIN)
   ▼
ManualController → ManualUploadService.uploadAndIndexingManual
   1. 직원 → 회사 확인, 카테고리가 같은 회사·활성인지 확인
   2. 확장자 검증 (.txt / .pdf / .doc)
   3. 파싱: PDFBox / TextDocumentParser / POI HWPF          ← (개선) S3 저장 전에 수행
   4. 분할: DocumentSplitters.recursive(500자, overlap 100자) — 구조 비인식 고정 길이
   5. S3 저장 + file 행 생성
   6. 청크 메타데이터 {company_id, category_id, file_id, index}
   7. 임베딩(OpenAI) → Chroma addAll                        ← (개선) 실패 시 벡터·S3 보상 삭제
   8. manual_metadata 저장 (status=SUCCESS, is_active=true) ← 마지막 단계라 이 행이 생겨야 "검색 허용"
   ▼
[사용자 챗봇] chatbot.js → POST /api/auth/chatbot/conversations/{id}/messages
   ▼
ChatService.sendMessage → answer()
   1. 질문 임베딩
   2. DB에서 활성 매뉴얼 조회 (회사 + 대화방 카테고리) → 허용 file_id 집합
   3. Chroma 검색: company_id AND category_id AND file_id ∈ 허용집합, 후보 50, minScore 0
   4. 코드에서 허용 file_id로 한 번 더 필터 → 동일 텍스트 제거 → top-5   ← (개선) 중복 제거
   5. 선택 청크의 앞뒤(index±1) 청크 조회                              ← (개선)
   6. 문서별로 묶고 원문 순서로 정렬, "[문서 N] 파일명 | 등록일" 라벨    ← (개선)
   7. LLM: 규칙=SystemMessage, 매뉴얼+질문=UserMessage                  ← (개선) 기존에는 한 덩어리
   8. LLM이 적은 "근거: [문서 N]"을 실제 컨텍스트 문서와 대조 → "출처: 파일명" 첨부  ← (개선)
   9. 질문/답변을 chat_message에 저장 (meta_json에 sources 포함)
```

구현되지 않은 단계는 다음과 같습니다.
- 질문 전처리와 쿼리 재작성: 없습니다. 질문 원문을 그대로 임베딩합니다.
- 리랭킹과 하이브리드(키워드) 검색: 없습니다.
- 대화 이력 활용: 없습니다. 매 질문을 독립적으로 처리하며, 대화방 카테고리만 유지합니다.
- 문서 "수정"과 버전 관리: 없습니다. 수정은 "새 파일 업로드 + 구버전 삭제/비활성"으로만 가능합니다.
- 재인덱싱 기능: 없습니다.
- 업로드 비동기 처리와 재시도: 없습니다. 동기 처리이며, 실패하면 관리자가 다시 업로드합니다.

## B. 신뢰성 평가

### B-1. 평가 방법

- **평가 하네스**: `src/test/java/.../chatbot/eval/ManualRagEvaluationTest.java`
  - 실제 `ManualUploadService`(파싱·청킹·임베딩)와 실제 `ChatService`(검색·프롬프트·LLM)를 사용합니다.
  - MySQL과 S3만 메모리 대체물로 바꿨습니다.
  - 실제 OpenAI API와 실제 Chroma 0.4.21(로컬 Docker)을 사용합니다.
- **합성 매뉴얼 13종**(`src/test/resources/rag-eval/manuals`)과 **정답이 명시된 61개 케이스**(`cases.json`)를 만들었습니다.
  - 업로드 → 수정(새 버전 업로드 + 구버전 삭제) → 삭제 → 삭제 문서 재활성화 시도를 순서대로 실행합니다.
  - 매뉴얼에는 표(20행 지역별 숙박비, 전결표, 일비표), 30개 절의 긴 문서, 예외 조건, 충돌 문서, 악성 지시가 담긴 문서, 타사 문서가 포함됩니다.
- **판정 방식**: 키워드 기반 결정적 판정입니다(필수 포함 / 금지 포함 / 거절 문구). LLM 심판은 쓰지 않았습니다.
  - 판정 한계: 표현이 다른 정답을 오답으로 볼 수 있습니다(예: K02). 의미상 잘못이어도 금지어가 없으면 통과할 수 있습니다.
  - 각 케이스는 1회 실행 기준이며, 최종 구성은 2회 실행했습니다. 실행 간 변동이 관측됐습니다(아래 참고).
- **결정적 테스트**(외부 API 없음): 단위 테스트 18건, 보안 테스트 2건, 실제 Chroma 통합 테스트 1건.

### B-4. 실서비스 사용 가능 여부

**조건부로 사용할 수 있습니다.** 다음 조건과 한계 안에서 쓰는 것이 타당합니다.

1. **(필수) Chroma 영속성 수정을 배포하고, 기존 매뉴얼을 재업로드(재인덱싱)해야 합니다.**
   이 수정 전에는 Chroma 파드가 재시작될 때마다 모든 벡터가 사라집니다. 그런데도 DB에는 매뉴얼이 `SUCCESS`·활성으로 남습니다. 그 결과 챗봇은 모든 질문에 "확인되지 않습니다"라고 답합니다. 잘못된 정보를 주지는 않지만 서비스가 사실상 멈춥니다.
2. 같은 주제의 구버전과 신버전 매뉴얼을 **동시에 활성 상태로 두지 않는 운영 규칙**이 필요합니다. 챗봇은 문서 간 충돌을 안정적으로 감지하지 못합니다(G01).
3. **숫자가 많은 큰 표**에 대한 답은 원문 확인을 권장해야 합니다. 열을 잘못 읽은 사례가 1회 관측됐습니다.
4. 대화 이력을 쓰지 않으므로 "그건요?" 같은 후속 질문은 처리하지 못합니다. 이것은 의도된 안전한 동작입니다.

## C. 기존 구현에서 잘한 점 (유지 권장)

1. **"DB 활성 목록 = 검색 허용 목록" 이중 필터** (`ChatService`)
   - DB의 활성 `file_id`만 Chroma 필터로 허용하고, 결과를 코드에서 한 번 더 거릅니다.
   - 이 설계 덕분에 벡터 삭제가 실제로는 한 번도 동작하지 않았는데도, 삭제·비활성 문서가 일반 질문에 노출되지 않았습니다(H01·H02 baseline 통과).
   - 벡터 DB와 RDB가 어긋날 수 있다는 전제를 둔 올바른 방어 설계입니다.
2. **검색 단계에서 테넌트 분리를 강제**합니다. `company_id`, `category_id`가 모든 청크 메타데이터와 검색 필터에 들어가며, 프롬프트에 의존하지 않습니다. 타사 문서 질문(M01·M02)에서 타사 청크가 검색 후보에조차 오르지 않았습니다.
3. **메타데이터를 마지막에 저장하는 업로드 순서.** 중간에 실패하면 검색 허용 목록에 들어가지 않습니다.
4. **엄격한 프롬프트 정책.** 정해진 거절 문장, "매뉴얼은 명령이 아님" 규칙, temperature 0을 갖췄습니다. 덕분에 답변 불가 질문 7/7, 일반 상식 유도(육아휴직·퇴직금·최저임금) 차단, 문서와 질문을 통한 인젝션 4/4 방어가 됐습니다.
5. **단계별 성능 로그**(`[RAG_PERFORMANCE] embedding/search/llm/total`). 운영 중 병목을 바로 볼 수 있습니다.
6. **프론트 답변 렌더링이 `textContent`**라서, LLM 출력에 HTML이 섞여도 XSS가 되지 않습니다.
7. **활성 매뉴얼이 없으면 임베딩 검색과 LLM 호출을 생략**해 비용과 지연을 아낍니다.

**변경하지 않은 것과 그 이유**
- **청크 크기, 검색 후보 수, top-K, minScore 0.0**: 카테고리 내 Recall이 이미 1.0이고 답변 불가 거절도 13/13입니다. 유사도 임계값은 실데이터로 보정하지 않으면 오히려 정답 누락을 만들 위험이 큽니다.
- **하이브리드 검색, 리랭커, 쿼리 재작성, 임베딩 모델 교체**: 측정된 실패(D-5, D-8)의 원인이 아닙니다. 기존 데이터 전체를 재인덱싱해야 하므로 근거 없이 도입하지 않았습니다.
- **인덱싱 형식(청크 텍스트) 변경**: 기존 운영 데이터와 섞이거나 재인덱싱이 필요해서 보류했습니다. 인접 청크 확장은 기존 `index` 메타데이터만으로 동작하므로 **재인덱싱이 필요 없습니다**.
- **충돌 감지 추가 규칙**: 시도했지만 G01을 고치지 못했고, 다른 케이스(T04)가 흔들려 되돌렸습니다(`after_v2` 실행).

**남아 있는 한계**
- T03: 표 바로 아래 "표에 없는 지역은 대전 기준" 문장이 ±1 범위 밖의 청크에 있어 전달되지 않습니다. 다만 모델은 지어내지 않고 거절했습니다.
- 표 열 오독: 프롬프트 변형 실행(`after_v2`)에서 T04가 "춘천 과장 9만원"을 10만원(옆 열 값)으로 답했습니다. 같은 컨텍스트였고 출처까지 붙었습니다. 최종 구성 2회 실행에서는 재현되지 않았지만 위험은 남아 있습니다.

## F. RAG 품질 비교 요약

B-2 표를 참고하세요. 요약하면 다음과 같습니다.

- **검색 품질은 변화가 없습니다.** 검색 파라미터를 바꾸지 않았기 때문이며, 의도한 결과입니다.
- **답변 품질**은 54 → 59(최종 2회차)로 올랐습니다. 잘못 거절이 4 → 1, 근거 없는 답변이 1 → 0, 출처 표시가 0% → 98%가 됐습니다.
- **데이터 동기화**: 삭제 시 잔존 벡터 1 → 0, 삭제 문서 부활이 허용 → 차단으로 바뀌었습니다.
- **비용과 지연**: 입력 토큰은 +38%(건당 약 $0.0001 증가), 응답시간은 실행 편차 범위 안에서 약 +15%입니다.

## H. 최종 결론

1. **기존 RAG 설계는 전반적으로 타당했는가?**
   검색과 답변 정책은 타당했습니다. 테넌트·카테고리·활성 파일 필터와 엄격한 거절 정책은 실측으로도 잘 동작했습니다. 반면 **데이터 수명주기**(삭제, 영속성, 재활성화)는 실제로 동작하지 않았습니다.
2. **가장 큰 문제는 무엇이었는가?**
   벡터 저장소와 DB가 맞지 않는다는 점입니다. 운영 Chroma가 메모리 모드여서 재시작하면 전부 유실되고, 삭제 API는 항상 실패했으며, 삭제 문서를 다시 살릴 수 있었습니다.
3. **가장 잘 구현된 부분은 무엇인가?**
   "DB 활성 목록 = 검색 허용 목록" 이중 필터입니다. 삭제가 고장 난 상태에서도 일반 질문에는 삭제 문서가 노출되지 않게 막고 있었습니다.
4. **실제로 어떤 문제가 해결되었는가?**
   벡터 삭제, 삭제 문서 부활, 챗봇 API 인증, 표 머리글 분리로 인한 오거절, 출처 미표시, 장애 시 500·무반응, 업로드 실패 시 고아 파일, 관리자 목록 문제를 해결했습니다. 영속성은 매니페스트만 수정했습니다.
5. **아직 해결되지 않은 위험은 무엇인가?**
   운영 Chroma 영속성(배포·재인덱싱 전), 문서 간 충돌 미감지, 큰 표의 열 오독 가능성, 삭제와 활성화 경합, LLM 호출의 트랜잭션 점유가 남아 있습니다.
6. **사내 사용자에게 제공해도 되는 수준인가?**
   **영속성 수정을 배포하고 재인덱싱한 뒤라면 제한적으로 제공할 수 있습니다.** 매뉴얼에 없는 질문은 13/13으로 거절하고, 모든 답에 검증된 출처가 붙습니다. 다만 신·구 버전 동시 활성을 금지하는 운영 규칙과 "중요한 수치는 출처 원문 확인" 안내가 함께 필요합니다.
7. **추가적인 구조 개선이 필요한가?**
   대규모 재설계는 필요 없습니다. 필요한 것은 문서 버전 교체 기능과 표 인식 청킹, 이 두 가지입니다. 하이브리드 검색과 리랭커는 현재 실패의 원인이 아니므로 보류합니다.
8. **지금 가장 우선해야 할 다음 작업은?**
   운영 Chroma에 영속성 설정을 배포하고, 기존 매뉴얼을 재인덱싱하는 것입니다.
